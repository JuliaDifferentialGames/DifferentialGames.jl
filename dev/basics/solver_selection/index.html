Solver Selection Guide

This page is generated from the solvers' solver_capabilities and the _solve method signatures in DifferentialGamesBaseSolvers.jl, not inferred from algorithm names. Cells marked unverified are not yet confirmed by a test in this documentation.

Decision workflow

  1. Is the game linear-quadratic on a shared state (LQGameProblem / LTVLQGameProblem)? → FNELQ for a feedback Nash equilibrium (exact).
  2. Are there stochastic LQ dynamics? → SFNELQ on a StochasticGameProblem.
  3. Nonlinear dynamics or costs, no constraints, feedback strategies wanted? → iLQGames.
  4. Control bounds, state bounds or shared (coupling) constraints? → ALGAMES (open-loop strategies).
  5. Lexicographic / prioritised objectives? → LIBR on a LexicographicGameProblem.
  6. Convex games with shared constraints, generalized or variational Nash? → YiPavel on a ConvexGameProblem.
  7. Recovering cost parameters from observed play? → InverseLQGames on an InverseGameProblem.
  8. Repeated solves along a moving horizon? → RecedingHorizonNash wrapping any inner solver.
  9. Bounded disturbances on a constrained receding-horizon game? → DynamicTubeMPC.
  10. Only a simulator, or very non-smooth costs? → the learning route: MADDPG in DifferentialGamesMARL, optionally guided by FNELQ.

The required_capabilities(game) function reports what a GameProblem needs; solve warns on a mismatch .

Rules of thumb

  • Declared capabilities are a necessary hint, not a guarantee: always read the solver's Known limitations.
  • A converged = true flag reports the solver's own stopping test. It is not an equilibrium certificate.
  • Different local solvers can return different local solutions of the same nonlinear problem.
